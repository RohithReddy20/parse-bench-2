## 3. Closing the Charts gap with open weights

Pure vector extraction vs pure VLM is the wrong split: **vector extraction nails geometry (0.1% precision) but fails semantics** (legend-to-color binding → -10 critical `"legend lost"`, panel boundaries, stacked-vs-grouped, dual axes, titles → -5 major), while **VLMs nail semantics but fail unlabeled axis reading** (58% of v1 points lacked printed labels, and 1 error >3× tol = -10 critical).

### Architecture: Vector-Hinted Chart Specialist VLM
1. **Panel & Chart Localization:** Detect chart boxes (heron / PP-DocLayoutV3) and split multi-panel figures via PDF axis-frame rectangles + sub-titles. Render each chart/panel crop at 300–400 DPI (≥1024px wide).
2. **Deterministic Vector Decompiler (born-digital, ~80–85% of charts):** From PDF paths (`pypdfium2`/`pdfplumber`), extract:
   - Axis lines, tick coordinates + tick text (linear vs log check, left/right dual axes, scale/unit strings),
   - Primitives grouped by fill/stroke RGB (bar rects → bottom-to-top deltas for stacked bars; polyline vertices sampled at x-tick x-coords; pie wedge arc angles / 360°),
   - Legend swatch RGBs + nearest label strings,
   - In-plot text labels verbatim (printed data labels — zero OCR digit risk).
   - Serialize as a compact JSON/Markdown **vector hint** (raw coordinates/values keyed by hex color + legend candidates + axis text).
3. **Fine-Tuned Chart VLM (high-res crop + vector hint → HTML `<table>`):**
   - Born-digital: VLM binds hex-color series to exact legend names, resolves stacked/dual-axis semantics, keeps printed labels verbatim, emits `<caption>Title / Panel</caption>` + clean HTML `<table>`.
   - Raster / low-confidence vector (~15–20%): run the same VLM on the high-res crop (with optional light coordinate-grid overlay) using **K=3–5 stochastic samples (T=0.35) + cell-wise numeric median aggregation** (reduces axis-read variance and digit slips at ~3× inference cost on only ~100 pages = <$0.50).
4. **Deterministic Verification Gate (CPU):**
   - Reject/retry if any series header matches placeholder/color patterns (`Series 1`, `Blue`, `Line 1` → prevents -10 critical `"legend lost"`),
   - Strip derived `Total`/`Average` rows unless explicitly plotted as a category (prevents -5 `"derived total"`),
   - Check unit compatibility between header/cells and chart axis text (prevents `NaN` column wipeout, [chart_next.py:2416-2432](https://github.com/run-llama/ParseBench/blob/6463ac1/src/parse_bench/evaluation/metrics/parse/chart_next.py#L2416-L2432)),
   - Verify all printed numeric labels inside the plot bbox appear in the output table (catches missed series/bars).

### Does SFT + GRPO fit in 37 Colab A100-40GB hours?
**Yes — for a 1.2B–4B LoRA chart-crop specialist.** The report ([L312](2026-11-23-parsebench2-research.md#L312)) dismisses GRPO based on full-page 7B olmOCR 2 costs, but cropped-chart GRPO is an order of magnitude smaller and has an exact millisecond reward right in the repo (`score_chart_tables`, [chart_next.py:3863](https://github.com/run-llama/ParseBench/blob/6463ac1/src/parse_bench/evaluation/metrics/parse/chart_next.py#L3863)):
- **Best base weights (Apache-2.0):** Benchmark `aeddix-labs/aeddix-alpine-ocr` (1.2B) and `ibm-granite/granite-vision-4.1-4b` (`<chart2csv>`) vs `LightOnOCR-3-4B` on your dev chart split first. A **1.2B** base gives ~3× more GRPO rollouts per A100-h; **4B LoRA (r=32–64, BF16 + grad ckpt ≈ 20–24 GB VRAM)** fits comfortably on 40GB.
- **Training set (permissive, zero PB2 leakage):**
  - 25k–30k diverse charts from `ibm-granite/ChartNet` (CDLA-P-2.0) oversampling unlabeled, stacked, multi-series, and dual-axis charts,
  - **10k–15k synthetic PDF charts** (rendered via `matplotlib`/`reportlab` on CPU) passed through your *actual* Stage 2 vector decompiler, with synthetic dropout/noise on vector hints so the VLM learns when to trust vs override geometry,
  - 5k `CoSyn-400K` charts (ODC-BY).
- **Exact time budget (37 A100-40GB hours):**
  - **SFT (~10–14h):** 40k crops × ~1,100 tokens ≈ 44M tok/epoch. At ~4.5–5.5k tok/s (4B LoRA) or ~12k tok/s (1.2B), 2 epochs take **~5h (4B)** or **~2h (1.2B)** → room for 2 iterations + ablations.
  - **GRPO (~16–20h):** 2,500 hard unlabeled/stacked/multi-panel prompts × `G=6` rollouts × ~350 output tokens ≈ 5.2M generated tokens. Reward = `chart_next` score (proportional F1 + severity floor directly penalizing wrong values, lost legends, derived totals, wrong units). With vLLM-colocated rollouts on 1×A100-40GB, 1.2B finishes in **~8–12h**; 4B LoRA finishes ~1,500–2,000 steps in **~16–20h**.
  - **Buffer/evals (~4–7h).**

### Permissive open models

2. **Secondary verifier / scanned-table specialist (pick 1 after dev ablation):**
   - **`dots.mocr` (`dots.ocr 1.5`)** — **83.40 Tables** ([leaderboard-v2.csv:53](https://github.com/run-llama/ParseBench/blob/6463ac1/leaderboard-v2.csv#L53)); verify its custom *dots.mocr License Agreement* (layered alongside MIT) before commercial use.
   - **`ibm-granite/granite-vision-4.1-4b`** (Apache-2.0, native `<tables_html>`) — unbenchmarked on PB2 CSV; high priority to test on scanned `complex_table_headers`.
   - **`MiniCPM-OCR-1.0`** (**80.60 Tables**, Apache-2.0) or **`aeddix-alpine-ocr` / `MinerU2.5-Pro-2605-1.2B`** (**80.58 Tables**, Apache-2.0; fast on crops).

### High-leverage pipeline & post-processing
- **Adaptive high-res crop re-reading:** Detect table boxes (heron + Inf2-Pro). Whenever a table is scanned, dense (>8 cols or >20 rows), or small-font (median height <7pt), crop with 12px padding at **300–400 DPI** (up to ~2048px) and re-parse with `Infinity-Parser2-Pro`.
- **Born-digital PDF text-layer cell snapping:** Align parsed HTML cell text to PDF words inside the table bbox. Snap numeric/currency/percentage/accounting-`(123)` cells to exact PDF strings (kills digit/sign criticals). Check for **unmapped horizontal lines of PDF text** inside the table bbox to catch silently dropped rows (each missing row = critical) and trigger a retry.
- **2-model disagreement gate on image-only tables (esp. `complex_table_headers`, 22/30 scanned):** Run Inf2-Pro + secondary model on crops. If row counts differ, span grids aren't rectangular, or >2 numeric cells disagree, run a higher-res / alternate-temperature retry and pick the structurally valid candidate with higher cross-model cell agreement.
- **Deterministic HTML post-processing aligned to `table_next`:**
  - Always emit HTML `<table>`, never Markdown (avoids empty-header left-propagation in [table_next.py:1242-1247](https://github.com/run-llama/ParseBench/blob/6463ac1/src/parse_bench/evaluation/metrics/parse/table_next.py#L1242-L1247)).
  - **Enforce rectangular span matrices:** validate/fix `rowspan`/`colspan` overflows per row so shifted cells don't cascade into wrong-number criticals.
  - **Multi-level `<th>` marking:** mark leading contiguous `colspan>1` rows + 1 leaf row as `<th>` (KDL's `header_mark` rule, [kdl_frontier_nano.py:2401-2441](https://github.com/run-llama/ParseBench/blob/6463ac1/src/parse_bench/inference/providers/parse/kdl_frontier_nano.py#L2401-L2441)).
  - **Preserve exact column order** (reordering = major), **preserve table title** in `<caption>` or line directly above ([table_next.py:2879-2887](https://github.com/run-llama/ParseBench/blob/6463ac1/src/parse_bench/evaluation/metrics/parse/table_next.py#L2879-L2887)), use HTML tags (`<b>`, `<sup>`, `<del>`, `<u>`) instead of Markdown emphasis inside `<td>`/`<th>` ([formatting_v2.py:485-494](https://github.com/run-llama/ParseBench/blob/6463ac1/src/parse_bench/evaluation/metrics/parse/formatting_v2.py#L485-L494)), and deduplicate repeated tables.

## 7. Is 85–89 realistic? What would it take to pass 90.93?

- **Is 85–89 realistic?** **Yes — 86.5–88.8 is realistic** for a permissive open-weight hybrid in this budget (central estimate **~87.8**). The report's upper end (89.7) assumes matching #1 overall on Layout (90) and beating #1 overall on Forms (87 vs Extend's 86.67), which is aggressive; hitting ~89.5–90.0 requires Charts ≥ 86 and zero regressions on scans.
- **What it takes to pass 90.93 (LlamaParse Agentic Plus):**
  - The **whole-board oracle across all 59 models (including Opus 5.5, Gemini 4 neon, Extend, Agentic Plus) is only 91.84**. Passing 90.93 means staying within **~0.85 pts/dimension of the best closed frontier model on Earth across all six dimensions** — e.g., `Text 91.5 / Fmt 93.0 / Tables 93.5 / Charts 90.0 / Layout 90.0 / Forms 87.6 = 90.93`.
  - **Gap that current budget + open weights cannot easily close:** scanned/handwritten pages (~33% of `text`, ~73% of `complex_table_headers`, dense scanned insurance tables, international scanned forms) where native PDF extraction gives **zero** lift, plus complex multi-panel/raster charts (where Agentic Plus spends ~42K input / 6K output tokens per page).
  - **Two concrete paths past 90.93:**
    1. **Pure open-weight (requires ~10–30× more training compute):** Fine-tune a strong 8B–27B VLM (SFT on 100k+ curated charts/tables/forms + multi-GPU GRPO directly on `table_next`/`chart_next`/`forms_v2`, ~500–2,000 H100-h) paired with an iterative render-and-verify chart agent.
    2. **Pragmatic hybrid within ~$15/run API spend:** Hit ~88.5–89.0 open-weight, then escalate the ~15% hardest scanned-table / raster-chart / handwritten pages to `GPT-6.2 sol (medium)` + `Gemini 4 neon (low)` / `Claude Opus 5.5` (adds ~2.0–2.8 overall → **~90.5–91.5**).
